The Working of Heimdall from First Principles

How Heimdall transforms incident response through deterministic safety gating, polyglot separation, and a type-safe gRPC contract.

1. The Root Problem: The Manual Incident Decision Tree

When an infrastructure incident occurs—such as a crash-looping Docker container, an out-of-memory (OOM) kill, or a failing network socket—engineers spend up to 80% of their Mean-Time-To-Diagnose (MTTD) executing a routine, manual investigative loop:

  1. Query status: docker ps or systemctl status.
  2. Collect stdout/stderr traces: docker logs --tail 100.
  3. Inspect runtime state: docker inspect <container> to extract exit codes and memory thresholds.
  4. Probe network dependencies: curl -I http://localhost:8080/health.

This manual loop is slow, repetitive, and context-switching intensive. However, handing this entire loop over to an unstructured LLM CLI wrapper introduces severe hazards: LLMs hallucinate non-existent files, invent fake log output, or execute catastrophic commands (e.g., rm -rf /).

2. First Principle: Probabilistic Reasoning vs. Deterministic Gating

Heimdall is designed around a fundamental separation of concerns:

  • The AI (Probabilistic): High-dimensional pattern matching, hypothesis formulation, and next-step reasoning. It answers: "Given these logs and exit code 137, what tool should I run next?"
  • The Systems Engine (Deterministic): Code-enforced safety gating, argument sanitization, and execution. It answers: "Is this tool permitted to run? Does this argument contain shell injection? Does the operator approve this write?"
Core Invariant: Zero AI Command Execution

The Python AI Worker is mathematically incapable of executing system commands. It can only emit structured JSON requests across gRPC. Every command is validated and executed by compiled Go code.

3. Why Polyglot Microservices (Go + Python)?

Why not write the entire application in Python or Go?

  • Go for the Core Gateway & CLI: Low memory footprint, fast startup times (<20ms), static compilation into a single binary, first-class native Docker SDK and systemd DBus bindings, and memory safety for security gating.
  • Python for the AI Reasoner: Native ecosystem for AI SDKs (Anthropic, LiteLLM, Pydantic, Instructor), dynamic prompt composition, and evaluation harnesses.

4. How Ticket 01 Establishes the Foundation

Ticket 01 implemented the cross-language spine: the gRPC Protocol Buffer contract in proto/v1/agent_service.proto.

Go Gateway (Host / Docker) Python AI Worker (Docker) │ │ │ ── DecideRequest(history, available_tools) ───► │ │ │ [Claude 3.5 Sonnet] │ ◄── DecideResponse(thought, tool_calls) ─────── │ │ │ [Permission Engine evaluates risk] │ [Go executes tool / asks operator] │ │ │ │ ── DecideRequest(history + tool_result) ──────► │

Three critical design decisions were embedded in Ticket 01:

  1. Polymorphic Stringified JSON Schemas: Tool input schemas and invocation arguments are passed as JSON strings (arguments_json). This decouples tool evolution from protobuf re-compilation.
  2. Unary Synchronous Turns: The RPC is unary (DecideNextStep). The Go Gateway remains the authoritative state machine; the Python worker is completely stateless per turn.
  3. Explicit ReAct Isolation: Reasoning (thought) is separated from actions (requested_tool_calls) and conclusions (final_answer), enabling real-time terminal streaming.

5. Interactive Knowledge Check

Why does the architecture forbid the Python AI Worker from directly executing shell commands on the host?
Python subprocess calls consume excessive system memory resources during triage.
Deterministic security boundaries must be strictly enforced by compiled Go code.
Docker containers cannot open local subprocesses without root privileges granted.
Claude 3.5 Sonnet requires gRPC protocol buffers to generate bash commands.
